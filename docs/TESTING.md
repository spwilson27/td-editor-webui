# Testing, validation and review

## 0. Setup

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt     # pytest + numpy (pinned)
(cd web && npm ci && npx playwright install chromium)                      # web unit / browser / e2e tests
.venv/bin/pytest td/tests -q                                                # pure Python tests (no TouchDesigner needed)
```

Python 3.11+ (CI: 3.11), Node 22+ (CI: 22). Live validation additionally needs TouchDesigner (a free non-commercial licence is enough;
tested with 2025.32820 on macOS). It is found in the standard install location of your OS, or set `TD_BIN` to the executable. The td-mcp
debug component is shipped in `tests/td/td_python_debug.tox`; no td-mcp checkout is required (`scripts/td_client.py` is a small built-in
client). Quick check: `.venv/bin/python scripts/td_workers.py --workers 1 --tier smoke`. Full workflow: `DEVELOPMENT.md`.

## 1. Test layers

| Layer | Tool | Location | Command |
| --- | --- | --- | --- |
| Pure TS logic (codec, colour math, history, rect math, flood-fill, store reducers, bridge) | vitest (node) | `web/tests/unit` | `cd web && npm test` |
| Canvas / WebGL code (surfaces, compositor + blend modes, tools, selection, undo, effects parity) and UI components | vitest browser mode, Playwright chromium, headless | `web/tests/browser` | `cd web && npm run test:browser` |
| UI + end-to-end (tools, layers, shortcuts, history, standby overlay, protocol round trip against a fake TD WebSocket server in node) | Playwright | `web/tests/e2e` | `cd web && npm run test:e2e` (builds and serves the app itself) |
| Typecheck | tsc | `web/` | `cd web && npm run typecheck` |
| Python: `protocol`, `frames`, `network`, `effects`, `ext` (fake TD objects), `upgrade`, tooling helpers, portability | pytest | `td/tests` | `.venv/bin/pytest td/tests -q` (`npm run test:py` from `web/`) |
| Live TouchDesigner validation | `scripts/td_workers.py` (isolated instances) / `scripts/validate_td.py` | `scripts/` | section 3; `docs/VALIDATION.md` |

`cd web && npm run check` = typecheck + unit + browser + e2e + pytest (no live TD; there is no lint step).
`PERF=0 VITE_PERF=0` skips the machine-dependent perf budget tests (CI does). Those budgets (and the live `timing` steps) are
load-sensitive: rerun alone on an idle machine before treating a failure as a regression.

Shared protocol fixtures (`docs/fixtures`, regenerated by `scripts/make_fixtures.py`) are decoded by both TS and Python tests.
CI (`.github/workflows/ci.yml`): `web` job (typecheck, unit, browser, build, e2e) and `python` job (pytest).

## 2. Required coverage

- Every module in `engine/`, `bridge/`, `td/raster_editor/` has tests. Line coverage
  ≥ 85 % for `engine` + `bridge` (vitest coverage, v8) and for `protocol.py` + `frames.py`.
- Pixel tests assert actual pixel values (with tolerance ≤ 2 per channel where blending is
  involved), not just "no throw".
- Every blend mode is checked against a reference formula on at least one pixel pair.
- Edge cases that must have tests: zero-size and out-of-bounds rects; brush stroke
  entirely outside the doc; single-click dab; fill on fully transparent layer; fill at
  tolerance 0 and 255; undo after resize; hidden/locked active layer; group opacity
  isolation; band splitting at exactly 2 MB; frame with wrong docW/H dropped; payload
  length mismatch; premultiply ⇄ unpremultiply round-trip incl. alpha 0 and 255;
  vertical flip; reconnect resends full frame; takeover switches active client.
- Performance tests (browser, skipped on CI-like slow runs with `PERF=0`): assert the
  budgets in DESIGN.md §6 for compositor and stroke dab throughput.

## 3. Live TD validation

Entry point (isolated, parallel; never touches an open project):

```bash
.venv/bin/python scripts/td_workers.py --tier smoke               # ~30 s: build, server, page, one paint parity, multi-editor
.venv/bin/python scripts/td_workers.py                            # full suite on up to 3 private TD instances (~3-7 min)
.venv/bin/python scripts/td_workers.py --only 12 --workers 1      # a single step, e.g. a timing step on an idle instance
.venv/bin/python scripts/td_workers.py --tier affected            # steps mapped from `git diff --name-only HEAD`, plus smoke
.venv/bin/python scripts/td_workers.py --no-timing                # skip timing-budget steps 7, 8, 12, 16
```

`scripts/validate_td.py` is the per-process step runner (`--only`, `--tier`, `--no-timing`, `--skip-ui`, `--json`, `--td-conn <connection file>`)
and holds the authoritative list of steps (`STEPS` table: ~60 numbered steps, each prints PASS/FAIL with numbers and its duration). Areas covered:
component build and no operator errors; web server and page load (not blank, connected); fake-client scene -> `out1` pixels; blend and
effect parity TD vs browser preview through the real UI driven by headless Playwright; TD view stream; latency and budgets; persistence
(`Exportdoc`, `.redoc`, history); inputs and TOP import; text/shape/transform/mask parity; multi-editor (tabs, election, failover, copy,
project load, Upgrade All Editors); deleting the component with clients connected (always last, step 99).

The real page is driven by `scripts/page_driver.mjs` (Playwright Chromium from `web/node_modules`) through `scripts/page_driver.py`; the old
Web Render TOP path remains behind `--page webrender`. A test hook `window.__editorTest` exists only with `?test=1` in the page URL (the
back channel is enabled by COMP storage `reTest`). Timing-sensitive steps are flagged in `DEVELOPMENT.md`. Design, measurements and the
safety model of the parallel runner: `docs/VALIDATION.md`.

## 4. Review checklist (reviewer agents)

Reviewers read the diff and the code it touches and run the tests themselves. Report
findings ranked by severity, each with file:line and a concrete failure scenario.

1. Correctness: matches DESIGN/PROTOCOL/TD_COMPONENT; off-by-one in rects, flips,
   premultiply maths, banding; event ordering; state after errors and reconnects.
2. Tests: required coverage above present and meaningful (would fail if the code broke);
   missing edge cases listed explicitly.
3. Performance: no allocations or `getImageData` of whole doc in per-pointer-event or
   per-frame paths; dirty-rect discipline; no O(doc) work per dab; TD main thread never
   blocks (no sync readbacks, no unbounded loops in callbacks).
4. Robustness: CEF compatibility (no too-new APIs), exceptions contained, no leaks
   (listeners, canvases, websockets), locked/hidden layers respected.
5. Fidelity to `design/editor.html` for UI work (spot-check screenshots).
6. Simplicity: no dead code, no speculative abstraction, matches surrounding style.
